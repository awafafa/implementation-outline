# 修改审查
## 输入

主 AI 通过 Skill 工具的 args 参数传入 JSON：

```json
{"旧数据路径": "实现纲要-{项目}.data.js.backup", "新数据路径": "实现纲要-{项目}.data.js",
 "用户指令": "用户的原始修改要求文本"}
```

---

## 核心铁律

**diff 中每一行变更——新增/删除/修改——都必须在用户指令明确授权的范围内，超出即拒绝。**

---

## 审查流程

### 1. 提取差异

1. 读取旧/新 `.data.js`，提取 `执行工作数据()` 函数体内的内容
2. 执行：`diff --unified=0 旧数据区 新数据区`
3. 从 diff 提取三类清单：
   - **删除清单** — `-` 开头的行
   - **新增清单** — `+` 开头的行
   - **修改清单** — 同一位置既有 `-` 又有 `+` 的行
4. diff 为空 → FAIL `[无变更]`

API 调用模式：`api.添加类/接口/结构体/枚举/函数/变量`、`api.设置责任映射/分组`、`代理.拥有/继承/实现/符合约定/符合/调用/依赖`、`代理.添加成员函数/变量/约束/测试`

### 2. 逐项验证

依次执行以下检查，**任一 FAIL 则整体 FAIL。**

#### 检查 1：删除（双重零容忍）

- **授权删除集合 A**：用户指令中明确出现删除关键词（删除/移除/去掉/删掉/不要/不需要）且指定了对象
- **实际删除集合 B**：从 diff 删除清单提取

| 条件 | 结果 |
|------|------|
| B 为空 | ✅ |
| A == B（逐条精确匹配） | ✅ |
| B 中有项不在 A | ❌ `[多余删除]` |
| A 中有项不在 B | ❌ `[未执行删除]` |

"修改"、"调整"、"把…改成…" 不算删除。

#### 检查 2：添加（含内容完整性）

- **要求添加集合 C**：用户指令中要求新增的内容
- **实际新增集合 D**：从 diff 新增清单提取

| 条件 | 结果 |
|------|------|
| C 中每项在 D 中有对应且**内容完整** | ✅ |
| C 中有项在 D 中未找到 | ❌ `[遗漏添加]` |
| C 中有项在 D 中找到了调用，但**内容不完整**（缺参数/缺描述/缺签名） | ❌ `[内容不完整]` |

#### 检查 2b：意图→API 类型映射

从用户指令提取意图，验证 diff 中是否有**正确类型**的 API 调用：

| 用户意图关键词 | 应使用的 API | 常见错误 |
|---|---|---|
| 字段/属性/成员变量 | `代理.添加变量()` | 只加了 `添加成员函数` |
| 解析模式/验证逻辑/约束条件 | `代理.添加约束()` | 只用责任描述代替 |
| 方法/函数/算法 | `代理.添加成员函数()` | 只在 `添加类` 描述中提及 |
| 职责概览 | `api.设置责任映射()` | 只在变量描述中提及 |
| 枚举/固定值 | `api.添加枚举()` | 用变量硬编码字符串 |

用户描述了"参数解析模式"但 diff 中无 `代理.添加约束()` → FAIL `[缺少约束]`。

#### 检查 2c：行为描述→推断添加物授权

用户指令经常描述**行为/效果**而非直接列出要添加的变量、函数、约束、测试项。审查必须从行为描述中推断出隐含的添加物，并将其纳入授权范围。

**推断规则：**

| 用户行为描述 | 合理推断的添加物 |
|---|---|
| "支持/增加/实现 X 机制/功能" | 实现 X 所需的成员函数、成员变量、约束、测试项 |
| "让 X 支持/兼容 Y" | 为 Y 添加的接口方法、适配变量、兼容约束、兼容测试 |
| "增加 X 校验/验证" | 校验函数、校验约束、校验失败测试项 |
| "支持 X 失败后 Y" | Y 行为函数、重试/回退变量、触发条件约束、失败场景测试 |
| "优化 X 性能/效率" | 缓存变量、缓存失效约束、性能测试项 |
| "X 需要可配置/可切换" | 配置变量、切换函数、配置约束、配置测试 |
| "规范化/统一 X 格式" | 格式化函数、格式约束、边界测试 |

**判定流程：**

1. 从用户指令提取行为描述
2. 按上表推断出隐含的添加物类别（函数/变量/约束/测试项）
3. diff 中的新增项若属于推断出的添加物类别，且其内容与行为描述**语义相关**，则视为已授权
4. diff 中的新增项既不在用户明确要求中，也不在推断范围内 → ❌ `[越权添加]`

**语义相关性判断：** 推断添加物的名称/描述应与行为描述指向同一目标。例如用户说"支持请求失败后自动重试"，推断出 `最大重试次数`（变量）、`重试请求()`（函数）、`失败后最多重试3次`（约束）—— 这些都与"失败后重试"语义相关 → ✅ 已授权。若此时 diff 中出现了 `日志格式`（变量）—— 与"失败后重试"无语义关联 → ❌ `[越权添加]`。

**注意：** 本检查只扩展授权范围（将合理推断的添加物纳入授权），不缩小范围。用户明确要求的内容仍按检查 2 验证。推断不成立时不应判 FAIL，应跳过该项交由检查 3 处理。

#### 检查 3：越权修改

- **授权对象集合**：用户指令中明确提及并要求变更的对象
- **实际变更对象集合**：从 diff 所有变更行提取

| 条件 | 结果 |
|------|------|
| 每条变更行对象 ∈ 授权对象集合 | ✅ |
| 有变更涉及了未授权对象 | ❌ `[越权修改]` |

⚠️ 看用户"要求变更"了什么，不是"提到"了什么。"给 认证服务 添加 登录"只授权了"添加登录"，若 diff 改了职责描述就是越权。

### 3. 输出判定

#### PASS 格式

```
审查结果: PASS
变更摘要: 新增 N 项 / 修改 M 项 / 删除 K 项
添加验证: 全部覆盖且内容完整 (N/N)
删除验证: 集合完全一致 (K/K)
越权修改: 无
```

#### FAIL 格式

```
审查结果: FAIL (N 项问题)
  [问题类型] 具体描述
  ...
```

问题类型：`[多余删除]` / `[未执行删除]` / `[遗漏添加]` / `[内容不完整]` / `[缺少约束]` / `[越权添加]` / `[越权修改]` / `[无变更]` / `[缺少内容]`

#### 典型 FAIL 示例

```
[缺少约束] 用户要求「JSON参数以模块为顶层字段解析」，应使用代理.添加约束()，但 diff 中仅更新了责任描述和成员变量，未添加约束
[遗漏添加] 用户要求添加「参数解析模式」，diff 新增清单中未找到对应调用
[越权修改] 用户指令「给 认证服务 添加 登录」中未授权改职责描述，实际改了职责字段
[多余删除] 用户授权删除：{旧验证器}，实际删除：{旧验证器, 令牌管理器.持有(数据库)}，多余：令牌管理器.持有(数据库)
[越权修改] 用户指令「添加测试项」中无删除要求，实际删除了用户仓库的责任映射
```
