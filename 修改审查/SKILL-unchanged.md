# 相同部分审查

> 本技能审查的是**未变更部分**——即旧文件和新文件中内容完全一致的行。验证其中是否存在根据用户指令应当变更但未变更、或应当删除但未删除的内容。  
> 与之配套的「差异审查」技能负责审查变更内容（diff）是否越权，本技能不涉及已变更部分。

## 输入

主 AI 通过 read 工具传入的上下文包含：

```json
{"旧数据路径": "实现纲要-{项目}.data.js.backup", "新数据路径": "实现纲要-{项目}.data.js",
 "用户指令": "用户的原始修改要求文本"}
```

以及一段**未变更部分预览**——即旧/新数据区中内容完全一致的行。

> 注：未变更部分已由调用方通过 difflib.SequenceMatcher 提取，仅包含 `.data.js` 的 `执行工作数据()` 函数体内的相同行，结构代码已排除。

---

## 核心铁律

**未变更部分中不应残留任何根据用户指令应当删除或应当变更的内容。结构性 API 调用（与用户指令无语义关联）不应被标记。**

---

## 审查流程

### 1. 提取授权变更范围

从用户指令解析出三类信息：

| 范围类型 | 解析方法 | 示例 |
|---|---|---|
| **应删除对象集合** | 用户指令中出现删除关键词（删除/移除/去掉/删掉/不要/不需要）且指定了对象 | "删除旧验证器" → {旧验证器} |
| **应变更对象集合** | 用户指令中出现修改关键词（改成/修改/调整/替换/更新）且指定了对象和目标 | "将英文名改成中文名" → {英文名→中文名} |
| **全局指令标识** | 用户指令中是否包含全量范围词（所有/全部/每一个/统一/批量/整体） | "将所有英文节点名改成中文" → 全局指令 |

- 若用户指令无删除要求 → 应删除对象集合为空
- 若用户指令无修改要求 → 应变更对象集合为空
- 若用户指令无全量范围词 → 非全局指令

API 调用模式：`api.添加类/接口/结构体/枚举/函数/变量`、`api.设置责任映射/分组`、`代理.拥有/继承/实现/符合约定/符合/调用/依赖`、`代理.添加成员函数/变量/约束/测试`

### 2. 逐项验证

依次执行以下检查，**任一 FAIL 则整体 FAIL。**

#### 检查 1：应删未删

- **前提**：用户指令中有明确的删除要求（应删除对象集合非空）
- 若用户无删除指令 → **跳过此检查**

| 条件 | 结果 |
|------|------|
| 未变更部分中未出现任何应删除对象 | ✅ |
| 未变更部分中仍有应删除对象残留 | ❌ `[应删未删]` |

**判定方法：** 在未变更部分中搜索应删除对象集合中的每一项。若某对象仍以原始形态出现（作为 API 调用对象、参数、描述文本等），则判定为应删未删。

#### 检查 2：应改未改

- **前提**：用户指令中有明确的修改要求（应变更对象集合非空）
- 若用户无修改指令 → **跳过此检查**

| 条件 | 结果 |
|------|------|
| 未变更部分中未出现任何应变更对象的旧形态 | ✅ |
| 未变更部分中仍有应变更对象以旧形态残留 | ❌ `[应改未改]` |

**判定方法：** 对应变更对象集合中的每一项（X→Y），在未变更部分中搜索 X 的旧形态。若 X 仍以旧形态出现且未被替换为 Y，则判定为应改未改。

⚠️ 注意区分"删除"和"修改"：用户说"删除 X"是删除要求，用户说"将 X 改成 Y"是修改要求。"修改/调整/替换"不算删除关键词。

#### 检查 3：全局覆盖验证

- **前提**：用户指令中包含全量范围词（所有/全部/每一个/统一/批量/整体），即全局指令
- 若非全局指令 → **跳过此检查**

| 条件 | 结果 |
|------|------|
| 未变更部分中无符合旧条件的残留对象 | ✅ |
| 未变更部分中仍有符合旧条件的对象未变更 | ❌ `[覆盖不全]` |

**验证方法：**

1. 从用户指令确定"匹配条件"和"目标变更"。例如"将所有英文名改成中文名" → 匹配条件=英文名称，目标变更=改为中文名称
2. 在**未变更部分**中搜索仍满足"匹配条件"的内容
3. 若找到未变更的匹配项 → FAIL `[覆盖不全]`，并列出具体未变更的项

**示例：**
- 用户指令"将所有英文节点名改成中文名" → 在未变更部分搜索仍为英文的节点名称 → 若有 `Host-服务:*`、`Client-*` 等未改为中文 → ❌ `[覆盖不全]`
- 用户指令"把所有接口的参数都加上类型注解" → 在未变更部分搜索缺少类型注解的参数 → 若有 → ❌ `[覆盖不全]`
- 用户指令"统一所有错误消息格式" → 在未变更部分搜索不符合统一格式的错误消息 → 若有 → ❌ `[覆盖不全]`

#### 检查 4：结构性代码排除

并非所有未变更内容都应被标记。以下内容**不应**判为问题：

| 排除类型 | 说明 | 示例 |
|---|---|---|
| 架构骨架调用 | 构成项目基础结构的 API 调用，与用户指令无语义关联 | `api.添加类("核心服务")` 若用户指令不涉及核心服务 |
| 无关对象 | 与用户指令指向的目标无语义关联的对象 | 用户要求改"认证服务"，未变更部分的"日志服务"不受影响 |
| 基础约定 | 不因用户指令而变化的底层约定 | 类型映射、基础继承关系等 |

**判定方法：** 对每一处疑似遗漏的未变更内容，判断其对象/名称是否与用户指令指向的目标有**语义关联**：
- 有语义关联 → 可能应改/应删 → 纳入检查 1/2/3
- 无语义关联 → 结构性代码 → 排除，不标记

⚠️ 语义关联判断应基于对象名称、功能描述、API 调用对象等，而非简单的字符串匹配。例如用户要求"认证服务添加登录"，未变更部分的"日志记录器"与"认证服务"无语义关联 → 排除。

### 3. 输出判定

#### PASS 格式

```
审查结果: PASS
检查摘要: 应删未删: 无 / 应改未改: 无 / 覆盖不全: 无
```

#### FAIL 格式

```
审查结果: FAIL (N 项问题)
  [问题类型] 具体描述
  ...
```

问题类型：`[应删未删]` / `[应改未改]` / `[覆盖不全]`

#### 典型 FAIL 示例

```
[应改未改] 用户要求「将所有英文节点名改成中文名」，未变更部分仍有 Host-服务:* 未改为中文
[应删未删] 用户要求删除「旧验证器」，未变更部分仍存在 代理.拥有(旧验证器)
[覆盖不全] 用户要求「所有接口参数都加上类型注解」，未变更部分中 getUser(id) 仍未加注解
```

#### 典型 PASS 示例（无删除/修改指令时）

```
审查结果: PASS
检查摘要: 应删未删: 无（用户无删除指令）/ 应改未改: 无（用户无修改指令）/ 覆盖不全: 无（非全局指令）
```
