## 核心目标

从需求文档中识别核心类型并建立它们之间的关系，画出项目的整体骨架。

这一步只关注"有什么类型"和"它们之间是什么关系"，不关注内部细节（成员函数、成员变量等）。

---

## 做什么

- 从需求文档识别核心类型：类、接口、结构体、枚举
- 识别自由函数（不属于任何类型的全局函数）
- 识别约定类型（隐藏规则的抽象）
- 建立类型之间的关系（拥有、继承、符合约定等）
- 标注每个类型的置信度（高/中/低）
- 标注每个类型/函数的责任映射（对应哪条需求）
- 设置分组（如果有必要）
- 识别成员变量和自由变量的存在与归属（但**不创建**，留到第二步）

---

## 不做什么

- 不写成员函数
- 不写成员变量
- 不写自由变量
- 不写函数签名
- 不写约束
- 不写测试

这些是第二步和第三步的事。

## 怎么想

### 类型识别

- 实体/角色 → 类/结构体
- 行为/能力 → 接口
- 独立操作 → 函数（自由函数）
- 枚举类别 → 枚举
- 全局数据/配置 → 变量（自由变量，不绑定到类型，**识别后留到第二步创建**）
- 类型内部的字段/属性 → 成员变量（绑定到父类型，**留到第二步通过 类型代理.添加变量() 创建**）

### 变量识别原则

- **第一步只识别变量/成员变量的存在与归属，不调用 API 创建**
- 避免类型树未稳定就过早录入字段，导致后续返工
- 第二步类型树定型后，再统一录入字段数据

### 枚举原则

- 枚举是一等类型节点
- 枚举节点可以拥有关系（其他节点可以引用/使用枚举）
- 枚举可以出现在拥有关系中
- 枚举可以被其他节点"使用"
- 枚举的枚举值应在 `.data.js` 中通过 API 完整定义

### 约定类型

- 约定类型是特殊的接口，创建时必须标记 `是约定类型: true`
- 约定关系从要求方指向约定类型（语义："我要求你满足这个约定"）
- 同一个普通类型可附加多个约定类型
- 当普通类型需要约定类型提供的约束时使用符合约定关系

### 关系建立

- 类型有向图（仅含类型节点时）只用拥有和继承关系，不用符合/调用/依赖
- 符合约定关系在第一步也可使用（标记约定类型）
- 符合/调用/依赖关系在第二步及以后使用
- 第一阶段可以用任意关系名字符串（如"管理"、"通知"、"参与"），这些自定义关系会在第二阶段被细化或替换为标准关系

### 置信度标注

- **高**：从需求文档直接提取，明确提到的类型
- **中**：从需求间接推断，根据上下文合理推断的类型
- **低**：AI 推测，需求中没有明确提及，需要重点讨论

---

## 关系类型

| 关系类型 | 语义 |
|----------|------|
| 拥有 | A 持有/包含 B |
| 继承 | A 继承/实现 B |
| 符合约定 | 要求方指向约定类型 |
| 符合 | B 满足 A 的条件 |
| 调用 | 函数/类型调用另一函数/类型 |
| 依赖 | 函数依赖某类型（应在该类型之后编写） |

> 第一阶段可以用任意关系名字符串。第二阶段引擎自动将第一阶段的 `代理.添加关系()` 调用替换为对应的具体方法。

---

## 常见错误

- 在第一步写成员函数/成员变量/自由变量 ❌
- 忘记标注置信度（默认"中"）
- 遗漏枚举类型
- 责任映射跳过了某些类型
- 接口写成了类（行为/能力 → 接口，实体 → 类/结构体）
- 不为每个父类型创建独立的数据容器类型
- 约定类型忘记标记 `是约定类型: true`
- 关系方向搞反（特别是继承和符合约定）
- 使用旧 API：`api.添加节点()`、`api.添加边()`、`节点类型` 枚举、`设置关系()` ❌
