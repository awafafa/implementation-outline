## 全局规则

以下规则适用于所有阶段，必须严格遵守：

| 规则 | 说明 |
|------|------|
| **先获取需求再开始** | 调用技能后第一件事是确认需求来源，没有需求文档或需求描述就询问用户 |
| **绝不修改模板文件** | 必须先将 `template.html` 和 `data.template.js` 拷贝到工作目录再操作，原始模板保持只读 |
| **每步必须审查** | 本步产出完成后，系统自动执行审查（浏览器验证 + 修改审查），审查 PASS 才能 AskUserQuestion |
| **每步必须用户确认** | 用户确认后才能进入下一步，不允许自动跳步 |
| **阶段分工明确** | 第一步不写成员/约束，第二步不写测试，各司其职 |
| **只使用公开 API** | 不直接操作内部数据结构，通过 API 进行所有操作 |
| **视觉表现不重要** | AI 只关注关系和结构的正确性，图的样式由引擎自动处理 |

## 核心目标

在第二步的基础上，完成最后的收尾工作：
1. **约束集中扫描**：确保约束完整、跨类型同步
2. **功能拆解**：将每个类型的职责拆解为独立功能点
3. **测试规划**：基于功能点 + 约束生成测试项

这一步结束后，实现纲要就完整了，可以交付给用户。

---

## 做什么

### 子步骤 1：约束集中扫描

- 调用 `api.导出全景图()` 获取所有节点/约束/功能的完整数据
- 检查每个类型 A 的约束，如果约束涉及类型 B，则将该约束也附加到类型 B 的约束列表中
- 确保每个类型的约束列表完整，无遗漏
- 检查约束是否重复、矛盾、冲突

### 子步骤 2：功能拆解

- 查看每个类型的"职责"字段，拆解为多个独立功能点
- 例如："处理用户登录、注册、token管理" → 登录 / 注册 / token刷新 / token过期处理
- 功能点应覆盖正常流程、边界条件、异常场景
- 将功能拆解写入节点的 `_功能拆解` 属性数组

### 子步骤 3：测试规划

- 基于功能点 + 约束，为每个类型和自由函数生成测试项
- 测试标题应同时考虑：功能正常流程、约束边界条件、异常场景
- 为每个自由函数添加测试列表
- 必要时为成员函数添加测试（可选）
- 测试项存储在 `_测试项` 属性数组中，不创建独立节点

---

## 不做什么

- 不创建新的类型节点或关系
- 不修改成员函数/变量的定义
- 不修改第一步和第二步已产出的内容
- 不修改约束本身（只做集中和同步，不改约束内容）

---

## 怎么想

### 约束集中原则

- 约束可能定义在 A 类型上，但实际影响 B 类型的使用者
- 这种情况下 B 类型的约束列表里也应该能看到这条约束
- 目的：使用任何类型时，一眼就能看到所有相关约束
- 约束集中不改变约束的定义，只是"引用"或"同步"

### 功能拆解原则

- 功能点是可独立验证的最小单元
- 每个功能点对应一个明确的用户价值或行为
- 功能拆解的粒度：既能独立测试，又不会太碎
- 功能点应覆盖：
  - 正常流程（主路径）
  - 边界条件（极端输入、临界值）
  - 异常场景（错误处理、失败路径）

### 测试规划原则

- 每个类型和自由函数都应该有测试项
- 测试项数量：每类型至少 2 个，越多越好但要有质量
- 测试标题要具体，不要笼统
  - ❌ 不好："测试登录功能"
  - ✅ 好："密码错误时返回401"
- 测试覆盖三个维度：
  1. **正常流程**：功能按预期工作
  2. **边界条件**：极端值、临界情况
  3. **异常场景**：错误输入、失败情况
- 测试项应对应到具体的功能点
- 约束条件应作为测试用例的重要来源

### 功能拆解和测试的关系

- 功能拆解 = "做什么"
- 测试规划 = "怎么验证做对了"
- 每个功能点至少应有一个测试项
- 约束条件应转化为测试用例

---

## 常见错误

- 忘记调用 `导出全景图()` 就开始写测试
- 测试项遗漏某些类型或自由函数
- 测试标题过于笼统（如"测试登录功能"），应具体（如"密码错误时返回401"）
- 未覆盖异常场景和边界条件
- 测试项作为独立节点创建（正确做法：作为属性添加）
- 功能拆解太粗（一个功能点包含太多行为）
- 功能拆解太细（每个操作都拆成一个功能点）
- 约束集中时改变了约束的原始定义
- 跳过约束集中直接写测试（可能遗漏跨类型约束）
