# 实现纲要

一份给写代码的人看的蓝图——不是传统的技术规划文档。产出文件：
- 实现纲要-{项目名}.html — 交互式有向图网页（静态壳，自动加载 .data.js）
- 实现纲要-{项目名}.data.js — 工作数据（在 `执行工作数据()` 函数中编写）

## 参考文档

AI 在执行过程中遇到以下疑问，应主动查阅对应文档：

| 文档 | 位置 | 用途 |
|------|------|------|
| API 参考 | `references/g6-api-quickref.md` | 所有 API 的用法、参数、返回值 |
| 第一步详细说明 | `steps/1-项目样貌.md` | 第一步的具体要求、思路、常见错误 |
| 第二步详细说明 | `steps/2-接口分化+实现约定.md` | 第二步的具体要求、思路、常见错误 |
| 第三步详细说明 | `steps/3-约束集中+测试规划.md` | 第三步的具体要求、思路、常见错误 |

## 模板使用规范

**红线：绝对不能直接修改技能目录下的模板文件。**

正确流程：
1. 将 `templates/template.html` 文件**拷贝**到工作目录，重命名为 `实现纲要-{项目名}.html`（静态壳，创建后不再编辑）
2. 将 `templates/data.template.js` 文件**拷贝**到工作目录（与 HTML 同目录），重命名为 `实现纲要-{项目名}.data.js`
3. 在 `.data.js` 文件中编写工作数据——在函数 `执行工作数据()` 内调用 API。HTML 是静态壳，会自动加载同名的 `.data.js` 并执行 `执行工作数据()`
4. 原始模板文件保持只读，永不修改

违反此规则直接污染技能模板，影响后续所有项目。

## 三步流程

每一步只关注一个维度，信息密度递增。

### 第一步：项目样貌

**核心目标：** 识别核心类型并建立它们之间的关系。

**做什么：**
- 从需求文档识别类型（类/接口/结构体/枚举）、自由函数、约定类型
- 建立类型之间的关系（拥有、继承、符合约定等）
- 标注每个类型的置信度和责任映射
- 只识别成员变量和自由变量的存在，不创建（留到第二步）

**详细说明：** 见 `steps/1-项目样貌.md`

### 第二步：接口分化 + 实现约定

**核心目标：** 穷尽式列出成员函数/成员变量 + 补全约束。

**两个子步骤：**
1. **接口分化：** 为每个类型添加成员函数、成员变量，补充自由变量
2. **实现约定：** 补全约束（参数约定、模板约定、实现注意事项）

引擎自动推断：成员函数/成员变量的拥有关系、函数返回值/参数类型的依赖关系、用到的变量的调用关系。

**详细说明：** 见 `steps/2-接口分化+实现约定.md`

### 第三步：约束集中 + 功能拆解 + 测试规划

**核心目标：** 集中扫描约束、拆解功能点、规划测试项。

**三个子步骤：**
1. **约束集中扫描：** 确保每个类型的约束列表完整，跨类型约束同步
2. **功能拆解：** 将每个类型的职责拆解为独立功能点
3. **测试规划：** 基于功能点 + 约束，为每个类型和自由函数生成测试项

**详细说明：** 见 `steps/3-约束集中+测试规划.md`
### 每步输出与推进规则（强制）

**每一步输出 `.data.js` 后，必须严格遵循以下顺序，不得跳过任何环节：**

1. **产出** — 完成当前步骤的 `.data.js` 内容写入
2. **审查** — 系统自动执行浏览器验证 + 修改审查（差异审查 + 相同部分审查），必须 PASS
3. **确认** — 审查 PASS 后，将当前步骤产出呈现给用户，请用户确认是否满意，并明确询问是否进入下一步
4. **推进** — 仅在用户明确同意后才执行下一步。用户要求修改时，按下方"用户修改流程"处理

**注意：**
- 用户可能在**第一步完成前**就提出修改要求。此时按"用户修改流程"处理，修改完成后重新走 审查 -> 用户确认 流程，再进入下一步
- 不得在未得到用户确认的情况下自动推进到下一步
- 不得将三步全部做完后才一次性审查——每步产出必须立即审查

## 核心规则：任何修改后必须自动审查

**这是最高优先级规则，覆盖所有场景：**

| 场景 | 操作顺序 |
|------|----------|
| 第一步：产出完成 | 写入 `.data.js` -> 系统自动审查（浏览器验证 + 修改审查）PASS -> 呈现给用户，询问是否进入下一步 |
| 第一步中：用户要求修改 | 备份 → spawn子代理修改 → 系统自动审查 PASS -> 重新呈现给用户，询问是否进入下一步 |
| 第二步：产出完成 | 写入 `.data.js` -> 系统自动审查 PASS -> 呈现给用户，询问是否进入下一步 |
| 第二步中：用户要求修改 | 备份 → spawn子代理修改 → 系统自动审查 PASS -> 重新呈现给用户，询问是否进入下一步 |
| 第三步：产出完成 | 写入 `.data.js` -> 系统自动审查 PASS -> 呈现给用户，宣布全部完成 |
| 第三步中：用户要求修改 | 备份 → spawn子代理修改 → 系统自动审查 PASS -> 重新呈现给用户，宣布全部完成 |
| 用户追问/确认 | 仅回答问题，不涉及文件修改 -> 无需审查 |

**判断标准：只要写入了 `.data.js` 文件，就必须审查。只读操作（回答问题、解释概念）无需审查。**

### 审查机制（系统自动执行）

审查由 `review-enforcer` 插件自动执行，主 AI 无需手动调用审查技能。插件在每次回合结束时自动执行：

1. **浏览器验证** — 通过本地 HTTP 服务器（`http://127.0.0.1:18080/`）用 Playwright 无头 Chromium 打开 HTML（自动加载 `.data.js`）。使用 HTTP 而非 `file:///` 是因为 `api.加载数据()` 使用同步 XHR，`file://` 下会被 CORS 拦截。HTTP 服务器审查后保留运行，用户可继续访问实现纲要。检查：
   - G6 加载、图实例、API 可用、节点数量 > 0
   - 无页面错误（`pageerror` 事件）
   - 无 `加载数据` 失败警告（引擎用 `console.warn` 报错，不触发 `pageerror`，需单独捕获）—— 验证外部数据确实已加载
   - 无悬空依赖（`导出全景图().边` 中每条边的目标必须存在于节点集合中——若 `加载数据` 缺失/失败/位置错误，`.依赖('外部项目.类型')` 会创建指向不存在节点的边）—— 验证调用方式正确、符合用户意图
2. **修改审查（差异审查 + 相同部分审查）** — 对比备份与新 `.data.js` 的 `执行工作数据()` 函数体，并行运行两个子代理：
   - 差异审查：检查变更内容（diff）是否在用户指令授权范围内
   - 相同部分审查：检查未变更部分是否存在应当变更但未变更的内容

**审查结果处理（插件自动）：**
- **PASS：** 插件放行，主 AI 将产出呈现给用户
- **FAIL：** 插件自动注入修复指令，主 AI 修复后重新审查，循环直到 PASS

### 审查通过后才告知用户

- **第一步/第二步完成后：** 审查 PASS -> 询问用户确认是否进入下一步
- 用户必须得要说出进入下一步的时候，才算是允许进入下一步，否则只能停留在当前的步骤中，等待用户审核，用户说出的其他的均是无效的进入下一步。
- **用户要求修改后：** 审查 PASS -> 回复用户修改已完成，列出关键变更
- **用户要求补充后：** 审查 PASS -> 回复用户补充已完成，列出新增内容

## 用户修改流程（强制，顺序不可颠倒）

每次用户要求修改 `.data.js` 时，必须按以下**严格顺序**执行：

1. **spawn 修改子代理** — spawn `modify-blueprint`，通过 SendMessage 发送增量修改指令。**禁止主 AI 直接修改 `.data.js` 文件。**
2. **系统自动审查** — 插件自动执行浏览器验证 + 修改审查（插件会自动在系统临时区创建备份，无需手动创建 `.backup` 文件）。**只有 PASS 才继续下一步。**
3. **完成** — 告知用户修改已完成。

红线：
- 审查未通过，绝不允许将结果呈现给用户
- 审查由插件自动执行，主 AI 无需手动调用
- 未经用户允许，不得进入下一步

## 核心概念

### 代理类型体系

每个节点对应一个代理对象，代理上有对应的方法。AI 不需要理解"节点"概念，直接调用具体类型的创建函数即可。

| 代理类型 | 创建方式 | 可调用方法 |
|----------|---------|-----------|
| 类型代理 | api.添加类 / 添加接口 / 添加结构体 / 添加枚举 | 拥有、继承、实现、符合约定、符合、调用、依赖、添加成员函数、添加变量、添加测试、添加约束、添加关系 |
| 函数代理 | api.添加函数 | 调用、依赖、符合、用到的变量、添加测试、添加约束、添加关系 |
| 变量代理 | api.添加变量 | 无特殊方法，存储数据 |
| 成员函数代理 | 类型代理.添加成员函数() | 调用、依赖、添加测试、添加约束 |
| 成员变量代理 | 类型代理.添加变量() | 无特殊方法，存储数据 |

### 关系类型体系

| 关系类型 | 语义 |
|----------|------|
| 拥有 | A 持有/包含 B（成员变量、成员函数或子类型） |
| 继承 | A 继承/实现 B |
| 实现 | A 显式实现接口 B |
| 符合约定 | A 遵守约定类型 B（要求方指向约定类型） |
| 符合 | A 满足 B 的设计时条件 |
| 调用 | A 调用 B（函数调用函数、函数调用类型） |
| 依赖 | A 依赖 B 类型（应在 B 之后编写） |

**约定类型 vs 接口：** 约定类型是特殊的接口（标记 `是约定类型: true`），代表函数/类型对使用者的隐藏要求。普通类型通过符合约定绑定到约定类型。

### 引擎自动推断（第二阶段）

第二阶段后，引擎自动根据代码建立以下关系，无需手动添加：

| 自动推断的关系 | 触发条件 |
|---------------|----------|
| 拥有 | 成员函数/成员变量被添加到类型后 |
| 调用 | 成员函数的实现中使用了另一个代理 |
| 依赖 | 成员函数/成员变量的类型使用了另一个代理 |

- 输出到项目工作目录

### 输出时机

- **每步完成后：** 输出对应深度的 `.data.js`
- **用户要求修改后：** 更新 `.data.js`

| 风险 | 概率 | 影响 | 缓解措施 |

## 核心约束

1. **先获取需求再开始** —— 调用技能后第一件事是确认需求来源，没有需求文档或需求描述就询问用户
2. **绝不修改模板文件** —— 必须先拷贝 `template.html` 和 `data.template.js` 到工作目录再操作
3. **任何修改后必须审查** —— 不只是步与步之间，用户要求修改/补充/修复后同样必须审查 PASS 后才能告知用户。这是最高优先级规则。
4. **每步必须用户确认** —— 用户确认后才能进入下一步
5. **三阶段分工明确** —— 第一步不写成员/约束，第二步不写测试，各司其职
6. **只使用公开 API** —— 不直接操作内部数据结构，通过 API 进行所有操作
7. **视觉表现不重要** —— AI 只关注关系和结构的正确性，图的样式由引擎自动处理

---

## 红线 —— 以下行为立即停止

1. **没有需求就开写** —— 调用技能后不确认需求来源直接开始写
2. **修改模板文件** —— 直接污染技能，影响所有项目
3. **跳过审查直接告知用户** —— 修改/补充/修复后跳过审查，把可能不一致的内容直接呈现给用户（红线第3条，最高优先级）
4. **编造不存在的需求** —— 凭空捏造需求条目和责任映射
5. **一步到位** —— 跳过第一/第二步直接写最终版，结构必然混乱
6. **直接操作内部 DOM** —— 绕过 API 直接改图或改 HTML，破坏数据一致性
