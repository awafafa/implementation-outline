# 追问模板

## 使用规则

- 每个追问必须提供候选答案（A/B，可选 C/D）
- 不追问需求文档中已明确的信息
- 优先追问 AI 置信度为"低"的项
- 每轮最多 5 个追问
- 用户回复"够了"/"就这样" → 结束追问

---

## 第一步追问（项目样貌阶段）

### Q1: 类型拆分/合并

```
"`{类型A}` 的职责包括 {职责1} 和 {职责2}。是否拆成两个独立类型？

A) 拆分为 `{候选类型1}` 和 `{候选类型2}`（推荐）
B) 保持 `{类型A}` 合并，通过成员函数区分职责
C) 部分拆分——把 {职责2} 分出去，{职责1} 保留"
```

### Q2: 依赖方向

```
"`{类型A}` 和 `{类型B}` 之间——谁应该依赖谁？

A) `{类型A}` 依赖 `{类型B}`（{理由}）
B) `{类型B}` 依赖 `{类型A}`（{理由}）
C) 互相不依赖，通过第三方协调"
```

### Q3: 遗漏类型

```
"需求中提到 `{功能描述}`——是否需要添加 `{候选类型}`？

A) 需要，添加 `{候选类型}`
B) 不需要，{功能描述} 可以由已有类型 `{已有类型}` 承担
C) 暂时不确定，第二步再决定"
```

### Q4: 继承/组合

```
"`{类型A}` 和 `{类型B}` 的关系应该是？

A) 继承——`{类型A}` 继承 `{类型B}`（{理由}）
B) 组合——`{类型A}` 持有 `{类型B}` 的实例
C) 不需要直接关系"
```

### Q5: 隐式约定

```
"需求中提到 `{描述}`——是否意味着存在隐式约定？

A) 是——当 {条件} 时触发 {效果}，需要画约定边
B) 不是约定，只是正常的函数调用
C) 部分正确——{修正后的约定}"
```

## 第二步追问（接口分化阶段）

### Q6: 函数归属

```
"`{函数名}()` 应该放在哪个类型？

A) `{类型A}`（{理由}）
B) `{类型B}`（{理由}）
C) 两个类型都需要各自的版本"
```

### Q7: 职责重叠

```
"`{函数A}()` 和 `{函数B}()` 的职责都涉及 {描述}。如何处理？

A) 合并为一个函数 `{合并后的函数名}()`
B) 保持独立——{函数A} 侧重 X，{函数B} 侧重 Y
C) `{函数A}()` 内部调用 `{函数B}()`"
```

### Q8: 缺失接口

```
"需求中提到 `{功能描述}`——是否需要在 `{类型}` 上添加函数？

A) 需要，添加 `{候选函数}()`
B) 不需要，{功能} 由现有接口覆盖
C) 需要，但应该放在另一个类型 `{替代类型}` 上"
```

### Q9: 特殊函数

```
"`{类型}` 是否需要显式的特殊函数？

A) 需要析构函数——{理由}
B) 需要转换函数——{理由}
C) 都需要
D) 都不需要，编译器默认生成即可"
```

### Q10: 签名确认

```
"`{函数名}()` 的签名需要现在确定吗？

A) 需要——我来描述：{签名描述}
B) 不需要，第三步再定
C) 只需要部分——返回值现在定，参数第三步定"
```

## 追问自检

生成追问后检查：
- [ ] 问题指向具体的类型或函数（非泛泛而谈）
- [ ] 提供了 A/B 候选答案
- [ ] 答案各有明确理由
- [ ] 标注了推荐选项
- [ ] 不重复已确认的信息
